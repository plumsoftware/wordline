# 8. Compose, архитектура и сборка

## 8.1. Матрица технологий

| Компонент | Решение v1 | Статус |
|---|---|---|
| UI | Нативный Jetpack Compose, Kotlin, Material 3 как основа семантики | Требование Compose от пользователя |
| Gradle | Wrapper 9.4.1 | Зафиксировано пользователем |
| AGP | 9.2.0 | Зафиксировано пользователем |
| JDK сборки | 17, одинаковый локально и в CI | Проектная база, соответствует минимуму AGP |
| Java/Kotlin bytecode target | 17 | Проектная база |
| minSdk | 26 | Проектное решение; не требование рекламной сети |
| compileSdk / targetSdk | 36 / 36 как стартовая база | Перед публикацией сверить требования выбранного магазина |
| Состояние | ViewModel, StateFlow, Coroutines | Однонаправленный поток данных |
| Хранилище | Room для прогресса, DataStore для настроек | Без облачного слоя |
| Сериализация | kotlinx.serialization или эквивалент с строгими лимитами | Закрепить точную версию на этапе 0 |
| Реклама | Yandex Mobile Ads; проверяемая исходная версия 8.6.0 | Версия из официального quick-start на момент исследования |
| DI | Явный AppContainer и constructor injection | Без обязательного Hilt/Koin в v1 |
| Сеть своей игры | Отсутствует | Не добавлять Retrofit «на будущее» |

Официальная [таблица AGP 9.2](https://developer.android.com/build/releases/agp-9-2-0-release-notes) указывает Gradle 9.4.1 и JDK 17; AGP поддерживает compile API до 37. Выбранный compileSdk 36 находится в пределах поддержки. Совместимость конкретного набора Room/KSP/Kotlin/Compose/Ads всё равно подтверждается реальной сборкой, а не одной таблицей AGP. [Gradle 9.4.1](https://docs.gradle.org/9.4.1/release-notes.html) закреплён точно, без динамического обновления Wrapper.

Точные версии Compose BOM, Activity, Lifecycle, Navigation, Room, DataStore, Coroutines, KSP и инструментов тестирования выбираются и фиксируются на этапе 0 после dependency-resolution и пробной сборки этого стека. Это ограниченный пункт подготовки, не разрешение оставить `latest`, `+` или SNAPSHOT в поставке. Результат этапа — таблица разрешённых версий и dependency locks в репозитории. Нельзя выдумывать номер BOM ради заполнения таблицы в ТЗ.

## 8.2. Особенность AGP 9

Использовать built-in Kotlin в Android-модулях. Не применять одновременно старый `org.jetbrains.kotlin.android` и встроенную поддержку AGP. Compose Compiler Gradle plugin `org.jetbrains.kotlin.plugin.compose` закрепляется в версии, соответствующей реально разрешённому Kotlin compiler. BOM Compose управляет версиями UI-библиотек, но не решает выбор компилятора. Не переносить старое `kotlinCompilerExtensionVersion` как способ настройки Kotlin 2.x.

Это следует из [миграции на built-in Kotlin](https://developer.android.com/build/migrate-to-built-in-kotlin) и [настройки Compose compiler](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler). Если версия KSP не совместима, сначала выбрать совместимый стабильный набор, а не отключать built-in Kotlin без документированного согласования. KAPT не нужен при выбранной Room/KSP-архитектуре.

## 8.3. Модули и зависимости

Рекомендуемые физические модули: `:app` (Activity, навигация, composable-экраны и контейнер), `:game-core` (чистый Kotlin: нормализация, проверка слова, сетка, дата/баланс), `:data` (Room, repositories, импорт/экспорт), `:ads` (адаптер SDK), `:content-tools` (JVM CLI валидации/упаковки). При росте UI из app выделяется `:design-system`; отдельный Gradle-модуль на каждый маленький экран не требуется.

Зависимости: app → core/data/ads; data → core; ads → небольшой рекламный контракт core либо отдельный API без игровых экранов; core не зависит от Android, Room и SDK. content-tools переиспользует чистую проверку core, но не входит в APK. Не допускать циклических зависимостей. Изображения и контент поставляются assets/resources без сетевого URL для обязательной игры.

## 8.4. Поток состояния

Composable принимает immutable UiState и callback onAction. ViewModel обрабатывает действие, вызывает use case/repository, публикует новый snapshot. Room Flow — источник сохранённого прогресса. В composable не выполнять SQL, выбор слов, списания, showAd и импорт. Сбор состояния lifecycle-aware, фоновые расчёты на Default/IO, UI на Main.

Критичные результаты представлены устойчивыми сущностями (CompletionResult, Ledger), а не только одноразовым Channel, который может быть потерян при пересоздании экрана. Transient-эффекты (звук, конфетти) имеют eventId и подтверждение показа; пропуск декора при process death допустим. Повтор подписки не повторяет денежное действие.

UiState игры: sessionId/revision, levelDefinition, displayCells, solvedSlots, selectedTokens, inputMode, bonusProgress, balance, hintAvailability, modal, loadingOperation, offlineHint. Не записывать каждый pointer move в ViewModel StateFlow всей страницы: локальное быстрое выделение может жить в state-holder круга; итоговый SubmitWord идёт в домен. Это уменьшает лишнюю recomposition без дублирования источника истины для принятого ответа.

## 8.5. Отрисовка поля и круга

Для сетки допустим Layout/Box с вычисленными координатами; текст букв остаётся настоящим Text/semantics, не единственным bitmap. Для соединительных линий — Canvas drawPath. У каждой letter-позиции стабильный key; shuffle меняет порядок tokenId без потери идентичности. Геометрия координат использует общий origin, density и measured bounds. Размеры не берутся из px макета как из dp.

Кэшировать статичный фон, paths и текстовые layout там, где это оправдано профилированием. Не аллоцировать списки и Bitmap на каждый move. pointerInput key не должен перезапускать распознавание от каждого изменения выбранного слова. Порядок hit testing тестируется чистой функцией. Системный back использует актуальный обработчик и не вызывает сохранение, уже выполняемое репозиторием.

## 8.6. Навигация

Использовать Navigation Compose со стабильными route и сериализуемыми ID, а не передачей всей LevelDefinition через аргументы. Маршруты: home, map, game(sessionId), result(resultId), tasks, calendar(month/date), collection, postcard(id), appearance, achievements, stats, settings, accessibility, save, article(type). Дочерние диалоги управляются состоянием текущего route, а не бесконтрольным push в back stack.

При импорте сбросить back stack на home с новым profileGenerationId. Deep links извне в игровые/файловые маршруты v1 не поддерживает. Экспортированные Activity/Provider ограничены фактическими системными сценариями. Share URI выдаётся через FileProvider с временным read grant, не file://.

## 8.7. Конфигурация Gradle

Kotlin DSL, version catalog `libs.versions.toml`, централизованные repositories. Основные источники google(), mavenCentral(), Gradle Plugin Portal для plugins; Yandex Maven только с content filter для нужных групп согласно документации сети. Никаких случайных приватных репозиториев и credentials в файле. В Wrapper задать точный distributionUrl 9.4.1-bin и официальный distributionSha256Sum, полученный при настройке. Не придумывать checksum.

Build types debug/release; отдельный QA-вариант при необходимости. Для одной RuStore-поставки не вводить лишние store flavors. Если владелец позднее добавит Google Play/AppGallery, оформить flavor и рекламные/manifest-различия отдельно. applicationId не назначен пользователем — временный namespace допустим только для прототипа; финальный уникальный ID нужен до регистрации РСЯ и подписи релиза.

Debug: демореклама, дебаг-меню, узнаваемый suffix, подробные локальные логи. Release: minify/R8 и shrinking ресурсов, отключённое debug-меню, реальные блоки, корректная подпись, versionCode растёт. Не решать ошибки R8 универсальным keep всего приложения. Для SDK использовать актуальные consumer rules и проверить реальную release-сборку.

## 8.8. Контент как часть сборки

До compile/package выполняется validateContent: уникальность ID, схемы, словарь/нормализация, буквы, связность и размеры сеток, определения для намёков, bonusPool, расписание, достижимые unlock-условия и наличие всех ресурсов. Ошибка любого обязательного уровня блокирует релиз с ID и понятной причиной. Сгенерированный manifest контента содержит версии и SHA-256. APK не должен содержать сырые генераторы, чужие необработанные словари и временные AI-варианты.

## 8.9. Производительность — цели для измерения

На физическом Android-устройстве среднего класса (4 GB RAM, 60 Hz), профиль release: холодный первый playable экран без миграции до 2.5 s p95 на 20 запусках; возврат тёплой игры до 1 s p95; обратная связь выбранной буквы до 50 ms p95; не менее 95% кадров активного ввода укладываются в 16.7 ms после прогрева. Бюджет PSS до 250 MiB в типовом игровом сценарии; APK до 100 MiB при базовом наборе, без жёсткого обещания до подготовки финальной графики.

Измерять Macrobenchmark/Perfetto и системные инструменты, устройство и сценарий записать в отчёт. Отдельно измерить после загрузки рекламного SDK; пики внешней рекламы описать, а не скрыть. Нет CPU-бесконечного игрового цикла при статичном поле; фоновые анимации останавливаются на lifecycle stop. Индексацию словаря делать вне Main, повторное открытие не переиндексирует всё.

## 8.10. Безопасность и доставка

Не хранить ключ подписи в репозитории, не включать секреты в BuildConfig и экспорт сохранения. AdUnitId не заменяет секрет подписи. Логи ограничены и не содержат персональных ID. Содержимое внешнего JSON не считается доверенным. Все собственные URL, если появятся для политики/поддержки, используют HTTPS; обязательный игровой контент не зависит от этих страниц.

CI из чистого checkout: проверить версии инструментов → разрешить закреплённые зависимости → validateContent → unit → lint → assembleDebug → release с R8 → instrumented/smoke по доступному устройству. Подпись релиза запускается только с настроенным защищённым secret storage. Сборка из чистого клона должна воспроизводиться по README без ручного редактирования исходников. Отсутствие владельческих данных должно сообщаться конкретно, не подменяться чужими ID.
